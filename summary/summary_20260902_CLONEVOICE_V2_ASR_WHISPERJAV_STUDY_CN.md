# tool_clonevoice_v2 ASR 能力研究：与 WhisperJAV 的对比及下阶段改进方向

日期：2026-09-02
参考项目：`reference/WhisperJAV-main`（v1.9 线）
本文关联记忆：`clonevoice-v2-inaudible-root-causes`、`subtitle-asr-translation-overhaul`、`clonevoice-feature-scope`

---

## 0. 一句话结论

我们和 WhisperJAV 用的是**同一批模型**，差别在**喂给模型的窗口**：我们把 28 秒连续音频交给 Whisper 然后事后清洗幻觉，
它把音频切成"一句一帧"（约 3 秒）再交给一个只输出文本的识别器、时间轴另取自 VAD。
我们那一整套 `HALLUCINATION_*` 常量和声学裁决，本质上是在事后收拾一个结构性问题。

---

## 1. 两边的 ASR 路径

### 我们（`tool_clonevoice_v2/segment_engine.py` → `tool_subtitle/logic.py`）

```
ffmpeg 16k mono
  → WhisperSeg(ONNX) VAD 概率  ─ 失败降级 → auditok ─ 失败降级 → 定长切块
  → 按 WHISPERSEG_MERGE_GAP_SECONDS=2.0 合并语音区，凑成 CHUNK_SECONDS=28.0 的块（重叠 2.0s）
  → faster-whisper（kotoba / large-v2 / large-v3）整块解码，word_timestamps=True
  → collect_segment_entries：词级锚定 + 词间隙 0.7s 拆行 + 能量谷 0.8s 二次拆
  → extend_entry_tails：修 DTW 系统性早 0.3~0.8s 的词尾
  → _filter_keep_timing：套话/重复/近重复/声学裁决 共约 10 类规则
```

### WhisperJAV 的 ChronosJAV（`pipelines/decoupled_pipeline.py` + `modules/subtitle_pipeline/`）

```
音频提取（enhancer=none 时 16k，否则 48k）
  → 场景切分（semantic / auditok / silero / none）
  → 【可选】语音增强，且支持"只用于 VAD"
  → TemporalFramer：VAD 分帧（max_group=3.0s, chunk_threshold=0.3s, pad ±100ms, threshold=0.25）
  → TextGenerator：anime-whisper / Qwen3-ASR，逐帧生成**纯文本**
  → TextCleaner：非语言行过滤等
  → TextAligner：可选 Qwen3 强制对齐（默认关闭，时间戳直接取自 VAD 帧，省约 1GB 显存）
  → Sentinel + Reconstruction + Hardening
```

四个组件（Framer / Generator / Cleaner / Aligner）都是 Protocol，可自由替换，这是它能不断接新模型的原因。

## 2. 关键差异清单

| 维度 | 我们 | WhisperJAV | 影响 |
|---|---|---|---|
| 解码窗口 | 28s 连续块 | ~3s VAD 帧 | **结构性**：28s 窗口正是 Whisper long-form attention collapse 的触发条件 |
| 时间戳来源 | 模型 DTW 词级，再用能量修 | VAD 帧边界（默认无对齐器） | 我们的 `extend_entry_tails` / `split_group_on_silence` 都是在修模型分段 |
| VAD 合并间隙 | 2.0s | 0.3s | 我们把整段对话并成一块，它保持一句一帧 |
| VAD 阈值档位 | standard .50 / high .35 / max .20 | JAV 默认 0.25 | 我们 high 偏保守、max 偏激进，中间有空档 |
| 识别器 | kotoba / large-v3 | anime-whisper / Qwen3-ASR / whisper-ja-1.5B(CT2) | 领域匹配的 finetune |
| 语音增强 | `DENOISE_FILTERS` 直接加在 ASR 输入 | 默认关闭；开启时可"只驱动 VAD" | 方向相反；他们明确警告降噪削辅音（pre-processing paradox） |
| 非语言行 | `HAS_LINGUISTIC_CONTENT_RE` 只判有无假名/汉字 | 证据检查 + 声效假名表两层 | `あぁん` 在我们这里**完整通过** |
| 多引擎 | 无 | 双通道 ensemble + 7 种合并策略 | 对字幕有效，对配音有重叠念读风险 |
| 效果测量 | 无 | `whisperjav/bench/`：CER + 时间 IoU + 漏/幻觉三分 | **我们靠单片人工听测** |

---

## 3. 为什么这些差异对"配音"比对"字幕"更要紧

1. **幻觉会被念出来。** 字幕里一条 `ご視聴ありがとうございました` 是噪声；配音里它是一句真被 IndexTTS 合成、
   压在画面上的话。我们的容错预算比字幕工具低一个数量级。
2. **边界即时长。** 克隆按段时长对齐（fit-to-duration），段边界必须是声学真边界。
   VAD 帧边界天然就是声学边界，而 Whisper 的段边界不是——我们为此写了整整两层修复。
3. **漏句与多句的代价不对称。** 漏一句 = 那里没有配音（可接受）；多一句 = 凭空多一句台词（不可接受）。
   我们目前两侧共用同一个 `vad_sensitivity`，没有把这个不对称做进参数里。

已有的实测正好印证结构性问题（见 `segment_engine.py` 尾部注释）：
`max` 档比 `high` 多放行 25% 语音，代价是 **12–15% 套话行**和 **31–46% 三字以下碎片**（`high` 档分别是 0–5% 和 3–13%）。
在帧级解码下这个取舍会松弛得多——放进来的是"这一帧确有语音"，而不是"这 28 秒里某处有语音"。

## 4. 改进方向（按性价比排序）

### A. 先建基准测量 —— 最高优先级

WhisperJAV 的 `whisperjav/bench/`（约 1500 行，只依赖 difflib + pysrt）：

- `loader.py` 读 GT / 测试 SRT
- `matcher.py` 按**时间重叠 + 文本相似度**贪心配对，产出 `matched / missed / hallucinated` 三类
- `metrics.py` NFKC 归一化（含剥离 `（佐藤）` 类说话人标签）后算字符级 CER + 时间 IoU
- `report.py` 多配置对比表；`provenance.py` 记录本次跑用的完整参数

我们没有等价物。HNVR-174 那次三根因定位是靠人工听 + 手工统计做出来的，成本极高、不可复现。
**没有这一步，下面 B–E 全都只能靠耳朵判断。**

我们的数据现状：4 部片子共 12 个 `.clone/` 工作目录，每个都留有 `audio16k.wav`（ASR 的真实输入）
和 `source.srt`（当时的 ASR 输出）。这意味着变体实验**不需要碰 10GB 的 8K 母片**，直接跑 `audio16k.wav` 即可。
但没有人工真值，所以基准分两种模式：

- **A/B 模式（现在就能用）**：变体 vs 基线，报告新增行 / 丢失行 / 套话命中率 / 单 token 非语言行率 /
  三字以下碎片率 / 语音覆盖秒数 / 时长分布。无需真值。
- **GT 模式（有人工真值时）**：移植 WhisperJAV 的 CER + IoU。

⚠️ 旧 `tool_subtitle` 的 `.jp.srt` **不是真值**（时长重排/合并把语音秒数灌水了，见记忆），只能比覆盖率和分段密度。

### B. 解耦式帧级解码 —— 结构性的那一刀

在 `segment_engine.py` 里加一条并行路径：VAD 帧（而非 28s chunk）→ 逐帧解码。两个成本级别：

- **低成本版**：仍用 kotoba/faster-whisper，只把窗口从 28s 换成 VAD 帧组。不换模型、不加依赖，
  先验证"窗口长度是不是主因"。**建议作为第一个实验。**
- **完全版**：日语走 `litagin/anime-whisper`（Whisper large-v2 在动画/JAV 对白上的 finetune）。
  `generators/anime_whisper.py` 适配器约 300 行，用底层 `WhisperProcessor + WhisperForConditionalGeneration`——
  注释明确说**不能用 HF `pipeline()`**，Windows + torch 2.9 + transformers 4.57 会 0xC0000409 硬崩。
  这条对我们直接有用（同类坑我们在 CTranslate2/cuDNN 上踩过）。

两个必须遵守的约束：

- anime-whisper 是**日语专用**。配音是通用功能（见 `clonevoice-feature-scope`），
  所以它只能进 `resolve_model_for_language` 的日语分支，kotoba / large-v3 保留为其他语言路径。
- 它**不出时间戳也不出词**。下游 `logic.py:522`（词级拆分）和 `diarize.py:877`（说话人切分）读 `words`。
  帧级路径下段边界够用（`logic.py:383` 已有 `words: []` 兼容分支），但**说话人归属要改成按帧判定**——
  这才是这条路真正的工程量，不是模型接入。

### C. VAD 分组参数 —— 当天就能试

WhisperJAV v1.9 的 JAV 调优默认值（记录在 `pipelines/AGENTS.md`，anime/qwen3 专用）：

```
max_group = 3.0s, chunk_threshold = 0.3s, start_pad = end_pad = 100ms, threshold = 0.25
```

对比我们：`CHUNK_SECONDS=28.0`、`WHISPERSEG_MERGE_GAP_SECONDS=2.0`、`high` 档 `speech_pad_ms=200`。
他们的 0.25 落在我们 `high`(0.35) 与 `max`(0.20) 之间——说明"high 偏保守 / max 偏激进"的判断是对的，中间还有空间。

（另注：他们的 `AGENTS.md` 记了一个值得警惕的教训——构造函数里一个 `generator_backend == "anime-whisper"`
分支在 kwargs 赋值**之后**无条件覆盖了分组参数，导致 GUI 滑块、CLI 参数、ensemble 默认值**全部静默失效**，
错误结论在文档里挂了 8 天才被纠正。我们的 `set_vad_sensitivity` → `base_asr_options` 链路也该有等价的回归测试。）

### D. 非语言行过滤 —— 对配音价值最大的小组件

`cleaners/nonlinguistic_utterance_filter.py` 两层判定：

1. **证据检查**：含汉字 / 助词 / 动词词尾 / 常用词 → 无条件保留
2. **声效假名检查**：剩余假名是否**全部**来自声效表（喘息 はひふへほ、亲吻 ちぢつづ、鼻音 んッー…）→ 全部命中则删

配套 `nonverbal_line_filter.py` 只删整行单 token（`あ。` `ん。` `ふっ。`），
作者在 MIMK-276 上实测命中 302/2414 行（12.5%）、零真实对白误杀，且明确**不碰**多 token 口吃（`あ、あ。`）、
笑声（`はは。`）、长音（`あー。`）、应答词（`うん。` `はい。`）。

我们的 `HAS_LINGUISTIC_CONTENT_RE` 只判断"有没有假名/汉字/字母"，`あぁん` 会完整通过，
然后被合成成一声叫床念出来。纯文本、零依赖、可直接移植，且保守设计正好符合我们的不对称容错。

### E. 只用增强音频驱动 VAD

WhisperJAV 的 "Enhance for VAD only"：增强后的音频只用来**定位语音**，模型听到的仍是原始音频
（避免降噪削掉区分辅音所需的高频）。

我们已经在配音路径上跑 bandit 分离，speech stem 是现成的。
记忆里的结论是这个 stem **不可信到能用于测电平**（失败偏差达 52 dB），
但"判断哪里有人说话"对分离失败的容忍度高得多。基本零额外算力：VAD 跑 stem，解码跑原声。
顺带该重测的是：我们现在的 `DENOISE_FILTERS`（`whisperx_backend.py:24`）加在 **ASR 输入**上，方向正好相反。

### F. 双通道 ensemble —— 建议不跟进

`ensemble/merge.py` 七种合并策略，对字幕（追 recall、重复行人眼能忽略）合理；
对配音，`full_merge` 一类会产出时间重叠的两条线，直接变成两句叠着念。
真要用只能 `pass1_primary` 且合并后强制去重叠。收益不确定、风险明确，排最后。

## 5. 执行顺序

1. **建 bench**（A/B 模式先行），用 12 个 `.clone/audio16k.wav` + `source.srt` 记下当前 production 基线数字。
2. **D**：非语言行过滤 —— 独立、低风险、对配音直接可感。
3. **C** + **E**：VAD 分组/阈值对照、stem 驱动 VAD —— 在 bench 上各跑一次**单变量**对照。
   （WhisperJAV 的原则值得照抄：一次只改一个。）
4. **B 的低成本版**：帧级窗口 + 现有 kotoba。若 bench 上幻觉率明显下降，说明窗口长度确实是主因，
   再决定是否上 anime-whisper 及随之而来的 diarize 改造。

## 8. 基准第一天就推翻了原计划的优先级

**原以为最该先做的是移植非语言行过滤（方向 D）。基准显示真正的头号缺陷是别的东西。**

22.7% 的行在归一化后只有三个字符或更少，HNVR-174 第 2 段高达 **47.1%**。
逐条看下去，它们不是短句，而是**被 28 秒分块解码撕成两半的词**：

```
230.09-230.15  ごめ          ← 两个字符，占 0.06 秒
231.57-232.05  ん
663.96-664.44  なんかそ
666.08-675.36  わ            ← 一个字符，占 9.3 秒
675.36-676.46  そわそわしてきちゃった
904.32-906.96  ご
906.96-907.34  ちそう
```

对配音而言这是灾难：每一半都被当成独立台词克隆，`わ` 拿到一条 9.3 秒的语音。

**更要命的是：这直接让 WhisperJAV 的非语言行过滤变成危险品。**
`ごめ`（ご+め）与 `ん` 的每一个假名都属于声效表，证据层查不到任何语法痕迹，
于是两半都会被判为"纯发声"删掉——一句真实的道歉就此消失。
把 WhisperJAV 的过滤器直接搬过来，会静默删除真台词。

## 9. 落地的两项修复（顺序本身就是修复的一部分）

### 9.1 撕裂碎行的重叠感知合并 —— `_merge_torn_fragments`

`tool_clonevoice_v2/segment_engine.py`。比 tool_subtitle 的
`merge_adjacent_fragments` 窄得多：**必须有一侧是碎片**（≤3 字），
两条完整短句永远不合并（那才是本管线刻意回避的"可读性改写"）。
时间保持声学真值——合并行从第一条的 start 到最后一条的 end，不发明任何时长。

三个细节都是被数据逼出来的：

- **重叠去重**：块之间重叠 2 秒，边界音频被解码两次，两半会共享接缝
  （`そわ` + `そわしてきちゃった`）。直接拼接会把 `そわ` 念两遍，
  所以先找最长共同接缝（上限 8 字）再拼。接缝被裁剪时 `words` 清空——
  词表已经拼不出文本了。
- **宽间隙例外**：撕裂的两半不一定挨着（`ごめ` 与 `ん` 差 1.42 秒，
  因为 `ごめ` 的时间戳只有 0.06 秒宽）。间隙上限放宽到 1.6 秒，
  但**仅当两侧都是碎片、且至少一侧本来就会被删**——
  此时合并是唯一不亏的结果。`はい` + `うん` 这种两侧都有语法证据的，永远不放宽。
- **合并在过滤之前**。实测这个顺序救回 10 行真台词：
  `めっちゃ気持ちいい`、`みーちゃん`、`んすごい光景だもんね`、`持ち`、
  `ごちそう`、`くなってる`、`いです`、`ごめん`……

### 9.2 非语言行过滤 —— `tool_subtitle/nonverbal.py` + `_nonverbal_reason`

分类器（证据层 + 声效假名层）单独成模块，删除**策略**留在 clonevoice 侧，
因为只有配音需要它——字幕里一行 `あぁん` 是眼睛会跳过的噪声，这里它会被念出来。

直接照搬 WhisperJAV 的列表在我们的语料上误杀率约 38%（53 条里约 20 条是真话）。
两处修正：

1. **补词表**：`じゃあ`、`いっぱい`、`おめえ`、`いっちゃ`、`ばいばい`、
   `やっぱ`、`こっち/そっち/どっち`、`ぜんぜん` —— 这些词整词都由声效假名拼成，
   不进白名单就必被删。另加**促音折叠**重试（`すっごい` → `すごい` 再查一次），
   这条只会保留更多、绝不会多删。
2. **三个字符以下不作判断**（`NONVERBAL_MIN_CHARS`）。分类器是在 WhisperJAV
   自己的帧级输出上调的，那种输出不撕词；我们的会。一两个字符里没有足够信息
   把 `ごめん` 的一半和一声呻吟分开，而分类器在这个长度上默认答"发声"。
3. 新增 **stretched 规则**：≥3 秒且 <1 字/秒的行是时间戳坏掉了
   （`メ` 摊 16.5 秒、`ん` 摊 25.3 秒）。但**长度和速率同样重要**——
   `みーちゃん` 摊 9.8 秒、`うまい` 摊 4.6 秒是同一个形状却是真台词，
   而短音频放进长槽位是配音本来就能处理的情况。所以只对
   ≤2 字、或任意长度的纯声效行开火。

### 9.3 实测效果（后处理重放，10 段全量）

| 指标 | 基线 | 修复后 | 变化 |

## 12. 步骤 3 —— 单变量解码对照（方向 C）

`scripts/asr_bench/decode.py`：每个变体只改一件事，跑同一批音频。

### 12.1 先解决"无真值就无法判优"的问题

`compare` 只能告诉你"变了什么"，不能告诉你"哪个更好"。
为此加了一个无需真值的质量指标：**`evidence_chars`** ——
带语法证据（汉字 / 助词 / 动词词尾 / 已知词）的行里的字符总数。

它能区分两种"多出来的行"：真正多认出来的话会抬高它；
把同一句话撕成更多碎片不会——撕开的两半失去了语法。
**必须与 fragment 数一起看，不能单独看。**

### 12.2 结果

| 变体 | 改了什么 | 行数 | evidence_chars | fragment% | glued% | sparse% | long_line% |
|---|---|---|---|---|---|---|---|
| control | （production） | 647 | 5239 | 20.7 | 0.6 | 1.1 | 1.2 |
| vad025 | VAD 阈值 0.35→0.25 | 672 | **5104** ↓2.6% | 23.5 | 0.9 | 1.5 | 1.2 |
| vadmax | VAD 档位 high→max | 696 | **5178** ↓1.2% | 23.3 | 0.6 | 1.4 | 1.0 |

### 12.3 结论

**改 VAD 门限没用，改解码窗口有用。**

- **vad025 与 vadmax 都比 control 差。** 两者都多出几十行，但 `evidence_chars`
  反而下降（−2.6% / −1.2%），vadmax 的 nonverbal 率还从 2.0% 涨到 3.3%、
  套话率 0.5%→0.6%。多放进来的是喘息，不是台词。
  这也正面否定了第 4 节 C 里"WhisperJAV 用 0.25，我们 high 偏保守"的推测——
  他们的 0.25 是配合 3 秒帧用的，脱离帧长照搬到 28 秒块上没有意义。
- **窗口一缩短，认出来的真实语言就多。** 8 秒块 +5.4%，
  再叠加 0.3 秒合并间隙 +7.5%，同时 sparse 和 long_line 双双下降
  （1.1%→1.0%、1.2%→0.8%）—— 短窗口下 DTW 没有那么多空间把一个词摊开。
- **代价是碎片率上升**（20.7% → 26.3%）：内容更多，但分成更多块送达。
  9.1 节的撕裂合并在这里做了大量工作（HNVR-174 #2 的 frame8 一轮合并了 40 行）。

这是第 0 节那个论点的第一份直接证据：**28 秒窗口本身就在让我们丢内容**，
而不只是让我们多出幻觉。方向 B（帧级解码）因此从"值得一试"升级为"已验证有效"，
而且**不需要换模型**就能拿到大部分收益。

## 17. 第二轮从 WhisperJAV 取到的东西

### 17.1 `CpsStartRetimer` → `tighten_entry_starts`（已落地，但收益极小）

他们的策略是对的：**时间戳坏掉时不要删行，而是钉住 end、把 start 往后移**
（`new_start = end - len(text) / 阅读速度`）。这解决了第 9.2 节里我用"删除"糊过去的问题。

但他们的估算方式不能照搬：7 字/秒是**阅读**速度，实测会把 `ごめん` 从 3.99s 压到 0.43s，
而一句拖长的 `ごめん` 真的会超过一秒——把配音放到槽位最末端会晚好几秒。
他们只能靠文本长度猜，因为**他们的过滤器跑在成品 SRT 上，手里没有音频**。

我们有。所以实现成了 `extend_entry_tails` 的镜像：那个沿有声帧向前走修早了的 end，
这个沿静音帧向前走修早了的 start。end 永不移动，因此起点只会变晚，不会制造新的重叠。

**实测收益很小：全语料只移动了 4 行、共 2 秒。** 原因是窗口改短之后，
sparse 行已经从基线的 66 条（4.0%）掉到 14 条（0.5%），这个缺陷基本自己消失了。
代码保留（约 50 行，有测试，零风险），但**不要以为它在这批素材上有用**。

### 17.2 `SceneOverlapResolver` → 测了，不需要

先量再动：当前输出里**完全嵌套的重复行 0 条**（我们的近重复去重已经处理掉了），
部分重叠 11 条 / 2486 行，其中 9 条 ≤0.35s（属于正常语音搭接与尾音延伸）。
对配音而言 0.2 秒的槽位重叠可以忽略。**不移植。**

## 19. 我之前报的 +4.9% / +7.9% / +25% 是错的

被问到"改进了多少"时我才第一次做端到端对比，然后发现两件事：

**（1）我一直没有真正的"改动前"基线。** 之前所有对比都拿 `control` 当基线，
但 `control` 已经包含了碎行合并和非语言过滤，所以那些数字只测了窗口一项，
从来不是总账。补了 `legacy` 变体（28s 窗口 + 三个修复全关）才有真正的 before。

**（2）`evidence_chars` 会把"碎片化"记成"收益"。** 这是致命的。

补测**汉字数**之后（日语的实词写作汉字，ASR 猜不出来时会退化成假名）：

| 配置 | 行数 | **汉字** | ev_chars | 汉字占比 | 每行字数 |
|---|---|---|---|---|---|
| legacy 28s（改动前） | 2514 | 2711 | 15592 | 17.4% | 6.2 |
| 28s + 修复 | 2210 | 2701 | 15819 | 17.1% | 7.2 |
| 28s + 修复 + 窗口上限 | 2225 | **2726** | 15826 | 17.2% | 7.1 |
| 3s + 修复 + 窗口上限 | 3318 | **2732** | 19551 | **14.0%** | 5.9 |

**汉字数在所有窗口下几乎不动（2701–2732）。** 字符数多了 25%，汉字只多了 0.2%——
那不是多认出了 25% 的话，而是**同一批话被切成多 50% 的行、而且拼错更多**。

读原文直接印证。28s 下的一整句：
```
もしかして私に変なことするつもりだったんじゃないでしょうね
```
3s 下变成四条：
```
もしかして / 私に変なことするつもりだった最高 / この音変態 / ケガラワシ
```
字数更多，`最低ね`→`最高` 错词，`汚らわしい` 退化成片假名 `ケガラワシ`。
Whisper 靠上下文选汉字，3 秒窗口加 `condition_on_previous_text=False` 等于不给上下文。

**已把 `CHUNK_SECONDS` 改回 28.0 / 2.0。** 对配音而言短窗口还额外有害：
行数 +50% 意味着一句话被拆成四条独立的克隆片段，中间有间隙。

**WhisperJAV 的 3s 分帧是和 anime-whisper 配套的**——一个为短对白微调过的识别器。
分帧和模型是一对，我把前者单独拿过来用在 kotoba 上，这就是错误的来源。

## 20. 真正查出来的一个 bug：超长窗口被 Whisper 静默截断

试 anime-whisper 时看到 156 条超过 8 秒的行，其中一条 **65 秒**——而窗口上限是 3 秒。
查下去发现 `split_audio_whisperseg` 的合并循环只限制**合并后**的区域长度，
**单个连续语音区自身超长时不做切分**。Whisper 的输入固定填充/截断到 30 秒，
所以那 65 秒里有 35 秒**从未进入模型**。

kotoba 路径下这个 bug 被掩盖了（faster-whisper 会在块内自己再分句），
但内容一样在丢。anime-whisper 一个窗口只出一段文本，缺陷才暴露出来。

修复：`quietest_split_point` —— 超长区按窗口上限切开，切点选"能装得下的最后三分之一"里
最安静的 20ms 帧，让刀落在换气而不是词中间。测试 `OverlongWindowTests`（4 条）。
收益：汉字 2701 → 2726（+0.9%），`long_line` 在 3s 下归零。小，但是纯正确性修复。

## 21. anime-whisper 实测：单行质量更好，但召回差 17%

模型已下到 `models/anime-whisper/`（含 `get_anime-whisper.txt` 下载引导，
格式与 kotoba / large-v3 一致）。实现见 `tool_clonevoice_v2/anime_whisper_backend.py`
与 `segment_engine.AnimeWhisperTranscriber`——VAD 分帧给时间轴，模型只出文本，
就是 ChronosJAV 的解耦形状。日语专用，其他语言自动回退。

| | 行数 | 汉字 | 汉字占比 | 每行字数 |
|---|---|---|---|---|
| kotoba 28s（现行） | 2225 | 2726 | 17.2% | 7.1 |
| anime-whisper 3s | 1583 | **2249** | 17.0% | **8.4** |

**单行确实更好**（同一段实测）：`キリにしてあげるね`→`綺麗にしてあげるね`、
`見るの?`→`寝るの?`、`なんでビキビクしてんの?`→`なんでビクビクしてんの?`，
还自带标点和读点；每行 8.4 字是所有配置里最完整的。

**但它对约 29% 的窗口只输出 `…`**（实测 58 窗口中 17 个），
整体汉字比 kotoba 少 17%。WhisperJAV 自己的文档也写了它"会漏掉非常微弱、孤立的语句"——
他们靠双通道 ensemble 补，我们没有。

**结论：不设为默认。** 代码和模型都留着，作为 `model_key="anime-whisper"` 可选。
要用它必须先解决召回：这正是 `pass1_primary` 式的**只补空档**合并该做的事——
我第 4 节 F 里一竿子否掉 ensemble 是过头了，会造成重叠念读的是 `full_merge` 一类，
只补空档的合并不会。

## 22. 这次改进的诚实总账

| 指标 | legacy（改动前） | 现行 | 变化 |
|---|---|---|---|
| **撕裂的词（glued_fragment）** | 264 | 17 | **−94%** |
| **孤立呻吟 token（lone_token）** | 56 | 0 | **−100%** |
| 纯发声行（nonverbal） | 159 | 51 | −68% |
| 每行字数（越大越完整） | 6.2 | 7.1 | +15% |
| 行数 | 2514 | 2225 | −11% |
| **汉字（认出的实词）** | 2711 | 2726 | **+0.6%** |
| 套话行 | 5 | 5 | 持平 |

**结论要说清楚：转录变干净了，但没有多认出内容。**
94% 的撕裂词被接回、所有孤立呻吟 token 被删掉、每行更完整——这些对配音是实打实的
（每条都会被 IndexTTS 念出来）。但"认出更多台词"这件事，**这次没有做到**，
汉字数只动了 0.6%。要真正提高召回，得走第 21 节那条路。

## 24. 关键事实：`source.srt` 不是 ASR 原始输出

10 段合计 1752 条里，校对**改写了 63 条（3.6%）、删除了 62 条（3.5%）**，
个别文件高达 18%。

所以 A 比 B 干净（每行 9.6 字 vs 6.2）不是因为当时 ASR 更好，
而是因为**后面有一道人工/LLM 校对把它擦干净了**。
我在第 7 节把 A 当作"当前 production 基线"是错的——那是校对后的成品，不是 ASR 的水平。

**这条重新定义了今天工作的价值**：碎行合并和非语言过滤做的事，
过去是甩给校对阶段去收拾的。而且有一类问题**校对根本修不了——时间**：
LLM 能把 `ごめ` 改成 `ごめん`，但它没法把 230.09 和 231.57 两条合并成一个正确的时间槽。

## 26. 下一步：anime-whisper 的窗口开错了，它其实更强

第 21 节判"anime-whisper 召回差 17%"是在 **3 秒**窗口下测的。补测更长窗口后翻案：

| 配置（子集 3 段 / 82 分钟） | 行数 | **汉字** | 每行字数 |
|---|---|---|---|
| kotoba 28s（现行） | 664 | 1049 | 8.0 |
| anime-whisper 3s | 529 | 986 | 9.0 |
| anime-whisper 8s | 321 | 1088 | 17.8 |
| **anime-whisper 15s** | 220 | **1185** | 27.6 |

**anime-whisper 在 15 秒窗口下认出的实词比 kotoba 多 13%**，而且只用了三分之一的行数。
它不是召回差，是我把窗口设成了 3 秒——那是 WhisperJAV 给"帧级 + 有对齐器"的管线用的。

**但 27.6 字/行对配音不能直接用**：一行 = 一个克隆片段，
15 秒里三句话会被当成一条台词念出来。

**所以卡点很明确：anime-whisper 需要长窗口才肯说话，配音需要短行。**
中间缺的正是一个**强制对齐器**——把 anime 输出的整段文本对回音频，拿到词级时间，
再用我们现成的 `_split_on_word_gaps` / 能量谷切分拆成一句一条。

好消息是这一步的代码**已经写好了**：`whisperx_backend.align()`（wav2vec2 强制对齐）
在 v2 里一直没被用上。缺的只是模型——`models/whisperx/wav2vec2-large-xlsr-53-japanese`
目前不存在，需要下载。

### 建议的下一步（按顺序）

1. **下载 wav2vec2 日语对齐模型**，补 `models/whisperx/get_whisperx.txt` 引导。
2. **接上 `AnimeWhisperTranscriber` → align → 现有拆行逻辑**，窗口设 15s。

3. **在 bench 上验收**，看两个指标：`kanji_chars`（内容量）与 `每行字数`
   （应回到 8–10，而不是 27.6）。**并且必须读原文**——这次的教训。
4. 若对齐质量不够，退路是 `pass1_primary` 式**只补空档**的双通道
   （anime 主 + kotoba 补空），只往空时间段插入，不会造成重叠念读。

# 第六部分：anime-whisper 接入结果（步骤 1–3 已执行）

## 27. 已做的三步

1. **对齐模型已下载**：`models/whisperx/wav2vec2-large-xlsr-53-japanese/`，
   附 `models/whisperx/get_whisperx.txt`（中英双语，含日语必需 / 中文可选两条，
   格式与 `get_kotoba-*.txt`、`get_anime-whisper.txt` 一致）。
2. **`AnimeWhisperTranscriber` 接上 15 秒窗口 + 切句**。
3. **bench 验收**（子集 3 段 / 82 分钟）。

## 28. 强制对齐这条路走不通（wav2vec2 在这类素材上塌了）

接上 whisperx 对齐后逐窗检查词级时间，发现是**退化解**：

```
窗口 15.6s 文本 'おはよう…起きてたの?んー…おかしい…'
  お@0.00-8.46 | は@8.46-8.48 | よ@8.48-8.50 | う@8.50-8.52 | …
  最大词间隙 0.00s
```

第一个字吃掉 8.46 秒，其余 18 个字每个 20ms（CTC 最小帧）。词表是查过的，
2155 个汉字条目，**不是覆盖问题**。这样的时间戳无法用来切句。

`_align_words` 保留在代码里，等有可用的对齐器时可以直接接上。

## 29. 改用 VAD 语音区切句

对齐器是猜的，**VAD 的语音区是测出来的**——那才是窗口内各句话真正的位置。
`place_on_regions`：一个语音区一行；句数与区数相等时一一对应，
不等时按各区时长比例分配文本，并把切点吸附到最近的标点（。！？、…）。

## 30. 结果：内容 +13%，但行结构还不能用

| 子集 3 段 / 82 分钟 | 行数 | **汉字** | ev_chars | 每行字数 | 超长行 |
|---|---|---|---|---|---|
| legacy 今早 | 754 | 1037 | 5172 | 6.9 | 7 |
| kotoba 28s（现行默认） | 664 | 1049 | 5321 | 8.0 | 9 |
| anime 15s 裸（一窗一行） | 220 | 1185 | 6083 | 27.6 | 132 |
| **anime 15s + 一区一行** | 318 | **1185** | 5965 | **18.8** | 92 |

**好的一面**：汉字 1185 vs kotoba 1049，**多认出 13% 的实词**。
读原文也确实更准：

```
kotoba: 同時ないように        anime: 動じないように     ← anime 对
kotoba: 活絶よく読むための訓練   anime: 活舌強く読むための訓練  ← anime 对
```

**两个拦路问题**：

1. **anime 对相当比例的窗口完全不写字**，所以同样的内容落在**一半的行数**里。
2. **按比例切文本会切断词**：`平常心を保つ訓練` 被切成 `常心を保つ訓練`，
   `あの次は何ですか` 只剩 `なんですか?`。配音会把这个残片念出来。

18.8 字/行是 kotoba 的两倍多，92 条超长行——**对配音还不能用**。

## 31. 结论与下一步

**默认仍然是 kotoba 28s。** anime-whisper 作为 `model_key="anime-whisper"` 的可选路径
保留（模型、代码、下载引导都已就位），类文档里写明了实验状态和两个拦路问题。

下一步只有两条现实路径：

- **A. 找一个能用的日语强制对齐器。** 有了真词级时间，切句就不再是按比例猜，
  `平常心` 这类切词问题自然消失，18.8 字/行也会掉到正常。
  候选：`reazon-research/reazonspeech`、Qwen3 forced-aligner（WhisperJAV 用的那个）、
  或用 kotoba 的词级时间戳给 anime 的文本做对齐（两模型跑同一段音频）。
- **B. 只补空档的双通道**：kotoba 主（保证行结构和召回），anime 只在
  kotoba 判低置信的行上替换文本。不改时间轴，因此没有切词和重叠风险，
  拿到的是 anime 的用词准确度而不是它的分句。

**B 的风险明显更低**，而且不依赖找到新模型——建议先做 B。

## 32. Qwen3-ASR：调研后排除（依赖冲突）

WhisperJAV 用的是 `Qwen/Qwen3-ASR-1.7B`（4.70 GB）加
`Qwen/Qwen3-ForcedAligner-0.6B`（1.84 GB，约 1.2 GB 显存）。
其中**对齐器本来是我们最需要的东西**——它能修掉第 30 节那个"按比例切文本会切断词"
（`平常心` → `常心`）的问题，而且它对任何文本都能用，不限于 Qwen 自己的输出。

**排除原因是依赖冲突，不是效果。** 两个模型都是 `model_type: qwen3_asr`，
**transformers 5.9.0 不认识这个类型**（`qwen3_asr in CONFIG_MAPPING_NAMES` 为 False），
必须装 PyPI 的 `qwen-asr>=0.0.6`，它自带 modeling 代码并且要求：

```
transformers      5.9.0  →  4.57.6   （本项目 pyproject.toml:24 明确 pin >=5.9.0）
huggingface-hub   1.17.0 →  0.36.2
accelerate        1.13.0 →  1.12.0
```

主环境降级会波及 IndexTTS-2.5 等全部组件，风险与收益不成比例。
独立 venv + 子进程（参照 CosyVoice3 的做法）在技术上可行，但要多维护一个环境、
多约 6.5 GB 模型和一层 IPC，**当前决定不做**。

若将来 transformers 主线支持 `qwen3_asr`，这条路可以直接重开——
届时最该拿的是那个 0.6B 对齐器，不是 1.7B 识别器。

# 第七部分：更正"对配音不能用"，并把权衡量化

## 33. 那句话是断言，实测后不成立

第 30 节写"18.8 字/行……对配音还不能用"，理由是"一行 = 一段克隆语音，
行里有停顿就会错位"。**理由本身对，但我没验证 anime 的行里到底有没有停顿。**

实测（子集 3 段，按 −45 dB 能量测每行内部最长静音）：

| | kotoba 28s | anime 15s（当时） |
|---|---|---|
| 行时长中位 | 2.00s | 4.92s |
| 行内最长静音 >1.0s 的行 | 2.7% | 23.6% |

**76% 的 anime 行是单段连续语音**，长一点根本不是问题——一个人连续说 3 秒
本来就是一句话，配一段连续语音是对的。真正有问题的只有那 23.6%。
而且其中一部分只是因为行长了 2.5 倍，机械上更容易包含一段安静。

## 34. 用现成的 `find_silence_runs` 把区再细分

`split_group_on_silence` 需要词级数据，anime 没有；但它底下的
`find_silence_runs` 只要音频。`_subdivide_regions` 用它把每个 VAD 语音区
按内部静音再切细（VAD 要 100ms 静音才结束一个区，所以一个区里仍可能装两句话）。

行内静音 >1s：**23.6% → 1.6%**，比 kotoba 的 2.7% 还好。

## 35. 但切文本的位置暴露了第二个问题

细分后区更多，按比例切文本的次数也更多。看原文才发现两种情况完全不同：

```
707.42  あの…次は、        ← 切在读点上，干净，文本没丢
708.76  なんですか?
713.62  平                ← 切在词中间，"平常心" 被劈开
715.52  常心を保つ訓練?
```

修法：`_nearest_break` 找不到标点时**返回 None 而不是硬切**，
该区并入下一区一起处理。"一行稍长" 是台词说得连了一点，
"半个词" 是配音念出一个残片——后者严重得多。

## 36. 最终权衡（子集 3 段 / 82 分钟）

| | kotoba 28s（现行默认） | anime 15s（最终） |
|---|---|---|
| 行数 | 664 | 365 |
| **汉字（实词）** | 1049 | **1185（+13%）** |
| 每行字数 | 8.0 | 16.2 |
| 行内静音 >1s | **2.7%** | 12.6% |
| 单字行（残片） | 3.6% | **1.4%** |
| 超长行 >8s | **9** | 72 |

**"anime 召回差" 这个说法也要收回。** 365 行装了 1185 个汉字，
664 行只装了 1049 个——**anime 不是漏台词，是把更多台词装进更少的行里。**

现在的权衡是清楚的：

- anime **赢**：实词 +13%，用词更准（`同時ないように`→`動じないように`、
  `活絶よく`→`活舌強く`），残片行更少（1.4% vs 3.6%）
- anime **输**：行长一倍，12.6% 的行内部含 >1s 停顿（kotoba 2.7%），超长行 72 vs 9

**剩下的问题是"配一段连续语音盖过一个 1 秒停顿"到底有多难听——
这个指标答不了，必须听。** 建议做一段两分钟的 A/B 成品对比再定，
在那之前默认仍然是 kotoba。

# 第八部分：两处更正 + 体积账（用户反馈后）

## 37. 更正：A/B 里那个"槽位装不下"是我的测试设计造成的

**译文长度本来就是跟着槽位走的**，短槽位只会得到一句短译文。

## 41. 回退链是这次唯一的风险点，已处理

anime-whisper 是 2.9 GB 可选下载，设为默认意味着**没下载的用户必须优雅回退**。
